# 社内問い合わせ管理システム 改訂版 基本設計

作成日：2026-10-13  
対象リポジトリ：<https://github.com/rin-sato-tech/inquiry-dx-django>  
Pythonパッケージ名：`inquiry_dx_django`  
文書の位置づけ：Django版の実装前に使用する設計案。既存版の優先順位・技術構成・データ構造には依存しない。

## 1. 目的と設計の前提

社員が一つのWebアプリで、問い合わせの新規登録、追加情報の提供、対応状況の確認を行えるようにする。担当者も同じアプリで受付から完了まで管理する。

目的は、転記の削減、対応漏れの防止、確認往復の記録、進捗の共有である。問い合わせ対応そのものの自動化は目的に含めない。

### 決定済みの方針

- Djangoによる単一のWebアプリを構築する。
- 社員向けの三つの操作をアプリ内で完結させる。
- Googleフォームは基本構成に含めない。
- Djangoテンプレートによる画面表示と、通常のHTTPフォーム送信を使用する。
- 公開コメントと内部メモを区別する。

### 本文で採用する設計上の仮定

- 社内の少人数の受付・対応担当者が利用する。想定件数は性能評価時に設定し、現行版の件数・削減率を実績として引き継がない。
- PostgreSQLを開発・検証・運用で使用する。
- 初期認証は管理者が発行したアカウントとパスワードによる。公開の自己登録は設けない。
- 対象は一般的な社内問い合わせ・依頼であり、専門的な申請・承認システムは作らない。
- 実データを使用しないデモとして開発し、実運用時には対象情報と運用体制を再確認する。

## 2. 対象業務と境界

| 対象 | 内容 |
|---|---|
| 問い合わせ受付 | 社員による登録、電話・口頭の代理登録 |
| 初期確認 | 内容確認、カテゴリ修正、担当割当、対応期限設定 |
| 対応 | 公開回答、追加情報の要求、社員からの返信、内部メモ |
| 進捗管理 | 状態変更、期限管理、再開、取消 |
| 記録 | 投稿履歴、担当・期限・状態の変更履歴 |
| 改善 | FAQ作成、問い合わせ傾向・滞留・作業時間の集計 |

カテゴリは、IT、総務、経理などの問い合わせ先を整理するための分類とする。閲覧範囲はカテゴリと別に設定し、分類変更によって自動的に公開範囲が広がらないようにする。

初期版では通常の問い合わせを対象にする。機微な人事相談などを含める場合は、専用の担当チームと閲覧範囲を設定する。複雑な承認、リアルタイムチャット、AI分類、外部システム連携、添付ファイルは初期版の完成条件に含めない。

### 受付情報と判断結果を分ける

社員が入力するのは、内容、業務への影響、希望日、希望理由である。担当者、対応期限、業務上の優先度は受付側が判断する。希望日と約束した対応期限を同じ項目にしない。

## 3. 利用者・権限

### 役割と対象範囲

全利用者は社員として自分の問い合わせを操作できる。受付・対応の役割は、その権限を追加する。所属部署だけで他人の問い合わせを閲覧できるようにはしない。

| 操作 | 社員としての操作 | 対応担当者 | 受付責任者 |
|---|---|---|---|
| 新規登録 | 自分の依頼を登録 | 同左 | 同左 |
| 一覧・詳細閲覧 | 自分の依頼 | 所属する対応チームの案件 | 管轄する対応チームの案件 |
| 公開コメント投稿 | 自分の未完了案件 | 自分に割り当てられた案件 | 管轄案件 |
| 内部メモ閲覧 | 不可 | 所属チームの案件 | 管轄案件 |
| 内部メモ投稿 | 不可 | 自分に割り当てられた案件 | 管轄案件 |
| 状態変更・完了 | 不可 | 自分に割り当てられた案件 | 管轄案件 |
| 担当・期限・優先度設定 | 不可 | 不可 | 管轄案件 |
| 代理登録 | 不可 | 不可 | 管轄案件を社員本人に代わって登録 |
| チーム間移管 | 不可 | 不可 | 移管元と移管先の双方を管轄する場合 |
| 集計・出力 | 自分の状況確認のみ | 所属チームの集計 | 管轄チームの集計・出力 |

受付担当者と受付責任者は初期版では一つの役割にまとめる。担当者が不在の場合、責任者が担当を変更する。自分の案件を他の担当者へ直接割り当てる機能は設けない。

システム管理者は利用者・チーム・カテゴリの設定を担当する。業務案件の閲覧は対応チームの所属で制御する。Djangoのsuperuserは全権限を持つため、通常業務の役割には使用せず、保守用アカウントとして扱う。

### 判定原則

- ログイン済みであることと、対象案件への権限があることを毎回確認する。
- 一覧、詳細、投稿、状態変更、CSV出力のすべてで同じ対象範囲を適用する。
- 他人の案件IDを指定しても閲覧・更新できない。対象外案件は404とする。
- 案件を閲覧できても操作権限がない場合は403とする。
- 社員向けには公開コメントだけを取得し、内部メモや変更履歴全体をHTMLへ出力しない。
- 社員から受け取った依頼者ID、担当者、状態、公開範囲などを信用しない。許可した入力項目だけを受け付ける。
- Djangoのグループ・モデル権限に加え、依頼者、チーム所属、担当者による案件単位の判定を実装する。

チーム変更では過去の内部メモも移管先に見える。責任者にその旨を表示し、必要な案件だけを移管する。初期版では同一案件を複数チームが共同管理する機能は設けない。

## 4. 業務フローと状態遷移

社員が登録すると「受付済み」となる。責任者が内容を確認して担当者を割り当て、担当者が対応を開始する。担当者は公開コメントで回答し、不足情報があれば返信を求める。社員の返信も同じ詳細画面に蓄積する。

| 状態 | 意味 |
|---|---|
| 受付済み / RECEIVED | 内容確認・担当割当・対応開始前 |
| 対応中 / IN_PROGRESS | 担当者が対応している |
| 依頼者回答待ち / WAITING_REQUESTER | 公開された質問への返信を待っている |
| 完了 / COMPLETED | 回答・処理を終えた |
| 取消 / CANCELLED | 依頼の撤回などで対応を打ち切った |

| 遷移 | 実行者 | 必須条件・処理 |
|---|---|---|
| 新規 → 受付済み | 社員・責任者 | 必須入力を満たす。依頼者と登録者を記録 |
| 受付済み → 対応中 | 担当者・責任者 | 有効な担当者が所属チーム内で設定されている |
| 対応中 → 依頼者回答待ち | 担当者・責任者 | 確認事項を公開コメントとして同時に保存 |
| 依頼者回答待ち → 対応中 | 依頼者の返信時に自動 | 公開コメントを保存し、待機開始日時を解除 |
| 依頼者回答待ち → 対応中 | 担当者・責任者 | 返信なしで再開する理由を記録 |
| 対応中 → 完了 | 担当者・責任者 | 依頼者向け完了回答を同時保存し、完了日時を設定 |
| 未完了 → 取消 | 責任者 | 依頼者向け取消理由を保存。取消日時を設定 |
| 完了 → 対応中 | 依頼者・担当者・責任者 | 再開理由、担当者の有効性を確認。完了日時を解除 |

依頼者が完了案件を再開する場合は「再開して追加情報を送る」という専用操作を使う。担当者が無効・不在の場合は責任者に再割当を依頼し、無効な担当者のまま再開しない。取消案件は再開せず、新しい依頼として登録する。

通常の追加投稿は未完了案件でのみ受け付ける。完了・取消案件では通常の投稿欄を表示せず、サーバー側でも拒否する。担当者の公開コメントだけで状態は自動変更しない。依頼者への確認依頼は専用の操作にする。

担当・期限設定だけでは状態を変更しない。期限超過・未割当は状態ではなく、案件を抽出する条件として扱う。回答待ちの間も対応期限を停止しない。

### 期限と通知の判定

- 希望日は任意。対応期限は受付後に設定し、未設定案件を別途表示する。
- 対応期限は日付として持ち、日本時間でその日の終了までを期限とする。
- 未完了かつ対応期限が今日より前なら期限超過とする。
- 依頼者回答待ちの継続時間はwaiting_sinceから計算する。
- 新規・未割当、期限未設定、期限超過、返信ありを担当者ホームで確認できるようにする。
- 「返信あり」は各担当者の閲覧日時と公開投稿時刻で判定する。全員共通の既読フラグは使わない。

## 5. データ設計

### 主要モデル

| モデル | 主な項目・役割 |
|---|---|
| User | AbstractUserを継承。表示名、所属部署、在籍状態。ログインにはusernameを使用 |
| Department | 部署名、有効フラグ |
| SupportTeam | 対応チーム名、有効フラグ |
| TeamMembership | 利用者、チーム、チーム内役割。組み合わせを一意にする |
| Category | カテゴリ名、初期振り分け先、有効フラグ |
| Inquiry | UUID、依頼者、登録者、受付時所属部署、件名、内容、カテゴリ、対応チーム、担当者、状態、影響、優先度、希望日、対応期限、各種日時、version |
| Comment | 問い合わせ、投稿者、本文、公開範囲PUBLIC/INTERNAL、種類、投稿日時 |
| InquiryEvent | 問い合わせ、操作した人、変更種類、変更前後、理由、日時 |
| InquiryReadState | 問い合わせ、閲覧者、最終閲覧日時。組み合わせを一意にする |

UUIDを内部IDとして使用し、その文字列表現を初期版の受付番号として表示する。連番発行やmax＋1方式は導入しない。IDが推測しにくくても閲覧権限の確認は省略しない。

カテゴリ別の追加項目は、初期版では共通の補足欄で扱う。実際に必要となったカテゴリだけ、項目と検証ルールを定義して追加する。利用者が自由にフォーム項目を設計する仕組みは作らない。

### データの制約

- 件名は必須で最大200文字。内容・コメントは空白のみを不可とし、初期上限は10,000文字。
- 依頼者はログイン利用者に固定。代理登録時だけ責任者が在籍社員を指定できる。
- 受付時所属部署を保存し、利用者の異動で過去の部署別集計が書き換わらないようにする。
- 担当者は案件の対応チームに所属する有効な利用者に限定する。
- 対応中、回答待ち、完了では担当者を必須とする。
- completed_atは現在の完了状態に対応する。再開前の完了日時はイベントに残す。
- cancelled_atは取消状態、waiting_sinceは回答待ち状態に対応する。
- 単一行の状態と日時の整合性、一意性はDB制約でも保証する。担当者のチーム所属など複数モデル間の条件は業務処理で検証する。
- 有効な担当案件を持つ利用者の無効化・チーム脱退は、再割当後に行う。
- 使用中の利用者、カテゴリ、チームは物理削除せず無効化する。過去の記録を保持する。
- 初期版では投稿とイベントの編集・削除機能を設けない。訂正は追加投稿で行う。

### 後続の機能で追加するモデル

| モデル | 用途 |
|---|---|
| WorkLog | 問い合わせ、担当者、作業日、区分、正の作業分数。管理作業と実対応を分ける |
| FAQ | 質問、回答、公開状態、対象範囲、作成者・公開者、関連問い合わせ |
| Notification | 通知種別、宛先、対象イベント、送信状態、試行回数、次回試行日時 |

通知はDBに送信予定を保存してから定期処理で送る。メール送信の失敗で投稿や状態更新を取り消さない。再送時の重複抑制は対象イベント・宛先・通知種別の組み合わせで行う。ただし、外部メール送信の完全な一度だけの配信は保証しない。

## 7. 技術構成と実装の分担

| 領域 | 採用方針 |
|---|---|
| Web | Django。導入時点でサポートされる安定版を選び、依存を固定 |
| 画面 | Djangoテンプレート、HTML/CSS。小さな表示補助のみJavaScriptを使用 |
| DB | PostgreSQL、Django ORM、マイグレーション |
| 認証 | セッション認証、標準のログイン・パスワード管理 |
| 入力 | Django Forms / ModelForm、サーバー側検証 |
| 環境管理 | uv、pyproject.toml、uv.lock、環境変数 |
| 検証 | Djangoのテスト基盤とPostgreSQLを使用 |
| 定期処理 | 後続段階で管理コマンド＋スケジューラ |

本番のホスティング先はこの設計では確定しない。実装時にはPostgreSQL、永続データ、HTTPS、バックアップを扱える環境を選定する。Djangoの開発サーバーは本番公開に使用しない。

### Djangoアプリの分割

- accounts：利用者、部署、チーム所属、認証関連。
- inquiries：問い合わせ、投稿、履歴、検索、状態遷移。
- knowledge：FAQ。FAQの実装段階で追加。
- reporting：集計・出力。分析機能の実装段階で追加。
- notifications：通知予定・送信処理。通知の実装段階で追加。

inquiries内では、models.pyに保存構造、forms.pyに入力検証、permissions.pyに権限判定、selectors.pyに閲覧範囲を含む検索、services.pyに登録・投稿・状態変更を置く。views.pyはHTTP入力と画面・業務処理をつなぐ。処理が増えるまではこれ以上分割しない。

新規登録、状態変更、担当変更、投稿の保存は業務処理を通す。通常のDjango adminから問い合わせを直接変更できるようにはしない。マスタと利用者管理を中心に使用し、業務モデルは必要なら閲覧専用にする。

### 更新時の整合性

- 問い合わせ更新、公開投稿、変更履歴を同じトランザクションで保存する。
- 更新対象の案件をロックし、取得後の状態に対して権限と遷移条件を再確認する。
- 状態・担当・期限の変更フォームにはversionを含め、古い画面からの更新は競合として再読込を促す。成功時にversionを増やす。
- コメント投稿は複数人からの追記を許容し、保存時点で案件状態を再確認する。
- 新規登録とコメント投稿には送信キーを付け、DBの一意制約で二重送信を抑制する。CSRFトークンとは別に扱う。
- 保存後はリダイレクトする。再読み込みだけでは再投稿しない。
- 通知を追加する場合、通知予定も同じトランザクションで保存する。

### 基本的な運用条件

CSRF対策、テンプレートの自動エスケープ、HTTPS、運用時のDEBUG無効化、秘密情報の環境変数化を使用する。利用者の本文をHTMLとしてそのまま描画しない。ログにはパスワードや問い合わせ本文を出さず、案件ID・操作・結果を中心に残す。

## 8. 最初の完成範囲と開発順序

最初の完成範囲は、ログイン、新規・代理登録、本人だけの一覧・詳細、担当割当、公開コメント、内部メモ、状態遷移、変更履歴、基本検索である。FAQ・通知・工数記録・分析は次の段階で追加する。

| 段階 | 作業 | 完成条件 |
|---|---|---|
| 1 | プロジェクト、PostgreSQL、カスタムUser、部署・チーム | デモ利用者でログインできる |
| 2 | 問い合わせ登録、社員向け一覧・詳細、権限 | 登録直後に本人が確認でき、他人は取得できない |
| 3 | 管理用一覧、担当割当、代理登録 | 未割当を確認し、対応を開始できる |
| 4 | 公開コメント、内部メモ、回答待ち | 社員と担当者が同じ案件で情報を追加できる |
| 5 | 完了・取消・再開、履歴、競合・二重送信対策 | 状態と履歴が整合し、誤った遷移を拒否する |
| 6 | FAQ、通知、工数記録、集計 | 機能ごとに定義した条件を満たす |

状態とデータ制約は段階1から定義し、必要な業務処理を順に実装する。履歴を後から全処理に付け直すのではなく、更新処理を作る段階で同時保存する。

## 9. 受入条件と検証

| 観点 | 必須の確認 |
|---|---|
| 登録 | 有効な入力で一件保存され、社員詳細へ遷移する。依頼者の改ざんを拒否する |
| 本人確認 | 社員Aが社員Bの詳細・投稿・再開URLへアクセスできない |
| チーム権限 | 管轄外チームの案件を一覧・詳細・出力から取得できない |
| 担当者権限 | 閲覧できる他担当者の案件でも、無権限の更新を拒否する |
| 公開範囲 | 内部メモと内部変更理由が社員向けHTMLに含まれない |
| 情報待ち | 確認依頼と状態が同時保存され、社員返信で対応中へ戻る |
| 完了・再開 | 完了回答必須。再開理由と各状態の日時が整合する |
| 競合 | 二人が古い画面から状態変更しても後の操作が上書きしない |
| 二重送信 | 同じ送信キーで問い合わせ・コメントが複数登録されない |
| 原子性 | 途中のエラーで、状態だけ・履歴だけが保存されない |
| 期限 | 日本時間の日付境界、未設定、完了・取消の除外を確認する |
| 管理設定 | チーム脱退・無効化が担当案件の整合性を壊さない |

単体テストは状態遷移・期限判定・権限判定を中心にする。HTTPの結合テストで改ざん・非公開情報・二重送信を確認する。ロック・競合の検証はPostgreSQLとトランザクションを使用し、SQLiteで代替しない。主要な社員・担当者操作はブラウザでも通して確認する。

## 10. 改善効果の評価

削減率は事前に断定しない。デモでは効果試算と実測を区別する。

| 指標 | 定義 |
|---|---|
| 受付件数 | 期間内に作成された問い合わせ件数 |
| 未完了件数 | 評価時点で受付済み・対応中・回答待ちの件数 |
| 期限超過率 | 未完了かつ期限設定済みの件数を分母、期限超過件数を分子とする |
| 初回公開回答までの時間 | 受付から担当者による最初の公開コメントまで。情報要求も含むと明記 |
| 完了までの時間 | 受付から完了までの経過時間。再開なし案件と再開あり案件を分ける |
| 確認往復数 | 回答待ちへの遷移回数。コメント件数とは区別する |
| 管理作業時間 | 工数記録の管理区分の合計。アプリ利用時間とは区別する |

初期集計は現在時点の状況を対象にする。過去時点の滞留を表示する場合はイベントから再構成し、現在状態の単純集計で代用しない。平均だけでなく中央値と件数も表示する。時間の初期定義は暦時間とし、営業時間による計算は別仕様とする。

## 11. 既存版との関係

既存の業務説明やデモデータは参考にできるが、画面とDBをそのまま移植する前提にはしない。現行の単一テーブルから、利用者・案件・投稿・変更履歴へ再構成する。

開発先は新しい独立リポジトリ `rin-sato-tech/inquiry-dx-django` とする。既存の `rin-sato-tech/inquiry-DXsystem` はStreamlit版の参考資料として扱う。Pythonパッケージ名にはハイフンを使えないため、`inquiry_dx_django` とする。新リポジトリの既存ファイルを確認してから初期構成を配置する。この文書はDjango版の基本設計とし、実装状況はREADMEと開発記録で管理する。

初期動作確認には新しいデモデータを使う。既存データの移行は別作業とし、利用者・カテゴリ・状態の対応表を定義する。過去に記録されていないコメント時刻や操作履歴を推測で作らない。旧IDは移行時の参照用として保持し、移行前後の件数と内容を検証する。

## 12. 実装前に使う具体例

### 正常な一往復

1. 社員Aが「社内システムにログインできない」を登録。状態は受付済み。
2. 受付責任者がITチーム内の担当者Bと対応期限を設定。
3. Bが対応を開始。状態は対応中。
4. Bが「表示されるエラー文を教えてください」と公開して回答待ちにする。
5. Aがエラー文を投稿。状態は対応中に戻る。
6. Bが内部メモに原因調査を記録。Aには表示されない。
7. Bが対処内容を公開して完了にする。
8. Aが詳細画面で完了と回答を確認する。

### 例外

- 社員CはAの受付番号を知っていても詳細を閲覧できない。
- 別チームの担当者は管理用URLを指定しても取得できない。
- 完了処理と社員投稿が競合した場合、保存時点の状態を確認し、完了後の通常投稿を拒否する。入力文を画面に戻し、再開操作を案内する。
- 新規登録で送信ボタンを二回押しても、一つの送信キーから作られる案件は一件だけである。
